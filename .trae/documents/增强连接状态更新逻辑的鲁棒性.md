### 连接状态更新问题分析

您提到：“下位机断了，然后重连上来，界面上没有显示已连接”。

经过代码分析，发现可能的原因如下：

1.  **TCP 事件传导**：
    *   `src/main/ipc/tcp.ts` (L143-148) 会监听 `tcpClientEvents.on('status')` 并通过 `tcp:status` 通道转发给前端。这部分看起来是正常的。

2.  **Store 状态更新 (`fishControlStore.ts`)**：
    *   在 `initListeners` -> `onStatus` 回调中 (L599-626)，当收到 `status` 事件时，会遍历 `fishMap` 并更新匹配 IP/Port 的鱼的 `connectionStates`。
    *   **关键点**：`onStatus` 回调中，如果 `status === 'connected'`，代码只做了 `stopReconnect(fish.id)`，并没有显式地做其他“强制刷新”操作。虽然 `connectionStates.value.set` (L604) 应该是响应式的，但有时候如果状态没有实质变化（例如之前因为重连逻辑已经设为 `connecting` 或其他），Vue 可能不会触发更新，或者更新滞后。

3.  **更重要的发现**：
    *   在 `onData` 回调中 (L629-636)，有一个逻辑：
        ```typescript
        if (connectionStates.value.get(fish.id) !== 'connected') {
            connectionStates.value.set(fish.id, 'connected')
            stopReconnect(fish.id)
        }
        ```
        这意味着**只要收到数据，就会强制设为已连接**。这本应是一个很好的保底机制。

4.  **推测原因**：
    *   可能 `onStatus` 中的 `connected` 事件触发时，`connectionStates` 更新了，但因为某种原因（例如组件未重新渲染，或者计算属性依赖未触发）UI 没变。
    *   或者，`tcp:status` 事件发送的 `ip` 和 `port` 与 `fishMap` 中存储的格式不完全一致（例如字符串/数字类型差异，或者空格），导致 `if (fish.satcomIp === ip && fish.satcomPort1 === port)` 判断失败。
    *   注意：`tcp.ts` 发送时 `ip` 是 string, `port` 是 number。store 中 `fish.satcomPort1` 也是 number。比较应该是安全的。但 `fish.satcomIp` 可能是 `null`？

### 修复计划

为了确保万无一失，我将在 `fishControlStore.ts` 的 `onStatus` 回调中，当状态为 `connected` 时，增加日志并**显式地、强制地**更新状态，并确保类型匹配。

同时，我会检查 `onData` 中的逻辑是否能覆盖这种情况（如果重连后没有立即发数据，可能就不会触发 `onData` 的连接状态更新，所以 `onStatus` 必须可靠）。

**具体修改**：
在 `fishControlStore.ts` 的 `onStatus` 回调中：
1.  加强 IP/Port 匹配的鲁棒性（转 String 比较）。
2.  确保 `connectionStates` 更新是响应式的。

此外，我还注意到 `startReconnect` 里面是 `setInterval`。如果 `connect` 成功了，`onStatus` 会被调用。
