### 连接状态更新与断线重连逻辑分析

经过分析 `fishControlStore.ts` 和 `TopBar.vue`，我发现当前的连接状态更新和重连逻辑如下：

1.  **连接状态更新机制**：
    *   Store 中通过 `initListeners` 监听了 `tcp:status` 和 `tcp:error` 事件。
    *   当收到 `tcp:status`（连接/断开）或 `tcp:error` 时，Store 会更新 `connectionStates`。
    *   **关键问题**：`TopBar.vue` 使用 `getStatusClass(currentFishStatus.status)` 来显示状态。而 `currentFishStatus` 是一个 `computed` 属性，依赖于 `allFishStatus`，后者又依赖于 `fishControlStore.connectionStates`。
    *   理论上，如果 Store 中的状态更新了，TopBar 应该会自动响应。如果您没有看到更新，可能是 `tcpManager` 发出的状态事件没有正确传导到 Store，或者 Store 的 `onStatus` 回调匹配逻辑有误（例如 IP/Port 不匹配）。

2.  **自动重连机制**：
    *   Store 中**已经实现**了自动重连逻辑 (`startReconnect`, `stopReconnect`)。
    *   在 `onError` 回调中（L688），如果发生错误，会调用 `startReconnect(fish.id)`。
    *   在 `connect` 方法中（L302），如果初次连接失败，也会调用 `startReconnect`。
    *   重连逻辑是每 5 秒尝试一次 `connect`，直到状态变为 `connected`。

3.  **您提到的问题**：“断线以后有没有重连，因为我在行不没看到更新链接状态”。
    *   这说明可能虽然有重连逻辑，但在**断线瞬间**，UI 并没有变成“断开”或“错误”状态，或者重连过程中没有显示“连接中”。
    *   或者，`tcpManager` 在断线时没有发出 `status: disconnected` 事件？

### 修复/优化计划

为了确保断线状态能及时更新并触发重连，我们需要做以下增强：

1.  **确保断线事件触发重连**：
    *   目前 Store 只在 `onError` 时触发重连。如果只是正常的 `disconnected`（例如服务端断开），Store 的 `onStatus` 会收到 `disconnected`，但**没有触发重连**（L591-604 中只处理了 `connected` 时停止重连）。
    *   **修改**：在 `onStatus` 中，如果状态变为 `disconnected`，也应该触发 `startReconnect`（除非是用户主动断开）。

2.  **区分主动断开与被动断开**：
    *   为了防止用户点击“断开”后还自动重连，我们需要一个标记，或者检查 `disconnect` 方法是否被调用。
    *   目前 Store 的 `disconnect` 方法会调用 `stopReconnect`，这很好。但如果随后收到 `disconnected` 事件，我们需要知道这是“预期的”还是“意外的”。
    *   **策略**：如果连接状态是 `disconnected` 且没有运行重连定时器，那么收到 `disconnected` 事件时，如果是被动断开（即我们认为它应该连接），则应该重连。但最简单的判断是：如果当前状态不是用户主动设定的 `disconnected`（比如之前是 `connected`），则触发重连。

3.  **UI 反馈**：
    *   确保 TopBar 能正确反映 `connecting` 状态。

我将修改 `fishControlStore.ts` 中的 `onStatus` 回调，增加对 `disconnected` 状态的处理，自动触发重连。

**具体修改**：
在 `src/renderer/src/store/fishControl.ts` 的 `initListeners` -> `onStatus` 回调中：
如果收到 `disconnected` 状态，检查是否应该重连（例如，如果该鱼之前是 `connected` 或者是活跃鱼，且不是用户主动断开的）。由于无法完美区分主动/被动，我们可以简单策略：**只要收到 disconnected 且当前不在重连中，就尝试重连**。但要注意 `disconnect` 动作会先清除定时器。

为了更智能，可以在 `disconnect` action 中设置一个 flag `isManuallyDisconnected`，或者在 `fish` 对象上记录期望状态。
不过最简单的修复是：**当收到 disconnected 事件时，如果该鱼不是正在被用户主动断开，就重连**。
由于 `disconnect` 函数是异步的，且会调用 `stopReconnect`。
如果在 `onStatus` 中看到 `disconnected`：
```typescript
if (status === 'disconnected') {
    // 自动重连？
    // 假设所有意外断开都需要重连
    // 除非我们刚刚调用了 disconnect()
    // 我们可以检查 connectionStates.value.get(fish.id)
    // 如果 Store 里认为是 'connected' 但收到了 'disconnected'，说明是意外断开 -> 重连
    const currentState = connectionStates.value.get(fish.id)
    if (currentState === 'connected' || currentState === 'connecting') {
         connectionStates.value.set(fish.id, 'disconnected') // Update UI first
         startReconnect(fish.id)
    }
}
```
这看起来是合理的。
