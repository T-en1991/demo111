根据您的反馈，我仔细梳理了声通连接的全生命周期，发现确实存在逻辑漏洞，导致“首次连接成功，退出再登录显示连接中（实际可能已连上）”的问题。

### 核心问题分析
1.  **监听器初始化过早且单一**：
    目前 `initListeners` 是在 `App.vue` 挂载时（`onMounted`）调用一次。当您退出登录时，我们在 `disconnect` 中清空了 `cleanupListeners` 并移除了监听器。
    **问题点**：再次登录时，`App.vue` 不会重新挂载，因此 `initListeners` **永远不会再次执行**。这导致第二次登录后，虽然 `connect` 建立了 TCP 连接，但前端根本没有监听状态变化和数据接收，所以 UI 永远卡在 `connecting`（因为收不到 `connected` 状态或数据包）。

2.  **状态同步机制缺失**：
    登录成功后，我们尝试连接。如果此时底层的 TCP 连接其实已经存在（比如上次退出没断干净，或者重连机制生效），`connect` 方法可能直接返回（或者因为状态不对而不做任何事），但前端的 `connectionStatus` 默认是 `disconnected`，且没有去主动“查询”当前的真实连接状态。

### 修复方案
我们需要重构连接管理的生命周期，确保“登录-退出-再登录”闭环的完整性。

#### 1. 移出 `App.vue` 中的初始化
`App.vue` 只负责全局 UI 结构，不应负责业务逻辑的生命周期。
*   **动作**：删除 `App.vue` 中的 `fishControlStore.initListeners()`。

#### 2. 在 `connect` 中启动监听
监听器应该伴随连接的建立而启动。
*   **动作**：在 `fishControlStore.connect()` 方法的开头，先调用 `initListeners()`。这样每次尝试连接时，都会确保监听器已就绪。

#### 3. 完善 `initListeners` 逻辑
确保监听器不会重复添加（防抖），并且在初始化时能主动处理“已连接”的情况。

#### 4. 优化 `disconnect`
退出时清理监听器（保持现状），确保下一次 `connect` 能在一个干净的环境下重新注册监听。

### 执行步骤
1.  **修改 `App.vue`**：移除 `onMounted` 中的 `initListeners` 调用。
2.  **修改 `store/fishControl.ts`**：
    *   在 `connect` 函数的第一行添加 `initListeners()`。
    *   确保 `initListeners` 内部先执行清理（`cleanupListeners`），防止重复注册。
    *   在 `login/index.vue` 中，保持登录成功后调用 `connect` 的逻辑不变。

这样，无论是首次登录还是退出重登，流程都变为：**登录 -> 调用 connect -> 注册监听 -> 发起 TCP 连接 -> 收到状态/数据 -> 更新 UI**，逻辑闭环且健壮。
